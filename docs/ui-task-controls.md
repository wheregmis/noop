# Confirmed task controls

The task page's Cancel and Done actions use `POST /api/tasks/cancel` from both cloud and local connections. Before showing a new task or plan confirmation, the UI checks `GET /api/stops/capabilities` for `family_stops: 1` from the primary, so an older primary must update before receiving the action. Active actions capture `host` and `run_id` before showing the confirmation dialog. A queued action sends `queued: true` and refuses a task that became active before execution; the owner can refresh and confirm that run explicitly.

Every claim gets a fresh UUID and retains its running host. The owning daemon registers that run before asynchronous preparation and binds its subprocess explicitly. Cancellation marks the run stopped before signaling, waits for its process tree and output streams, and only then persists done or cancelled state under the shared record lock. Process completion, account failover and follow-up generation recheck the same run fence after asynchronous work.

On POSIX systems the owned tree is suspended before forced termination, so a termination handler cannot create new detached work during shutdown. An already-exited or unverifiable parent does not become a successful stop: its task and PID binding remain available for inspection. Historical daemonized descendants cannot be reconstructed from an exited parent.

For a remote run the primary dispatches a narrow task-control command to the claiming machine. Family-aware workers advertise `task_api: 2`; older single-run workers must update and reconnect before receiving a stop. Their account and project channels remain available. The command identity includes protocol version, host, task, run and requested outcome, so transport retries reuse one command without accepting an older single-run receipt. Workers cannot issue controls to other machines. Successful results must match the exact identity and outcome; offline machines, missing support, conflicting runs and unconfirmed synchronization remain visible failures. The primary does not manufacture another machine's terminal task record.

The UI assigns an idempotency key to each confirmed intent. Cloud UI receipts scope it to the owner session and return the same ticket after a lost initial response. A stable UI-ticket key also reaches the primary's private receipt engine. Direct local calls use the same engine. Completed and uncertain requests are not re-applied; only a proven failed refresh can retry. A fresh owner action gets a different key, even when its task and requested outcome match an earlier action.

Cancelling a plan or ending a parent task also captures its related work. Queued descendants are terminalized in the same refreshed mutation. Active descendants receive durable stop intents containing their original host, task and run UUID; the plan or parent retains a `pending_stops` batch and operation UUID. Missing or unverifiable identities remain visible as unresolved work. The original targets are retained rather than rebound to a later run.

The primary coordinates those remaining stops. It refreshes and captures progress under the file lock, invokes exact-run controls outside the lock, then refreshes again before removing confirmed targets. A successful command alone is insufficient: the shared mirror must contain the matching terminal run without a conflicting active attempt. Failed synchronization or a disconnected worker returns an explicit partial `503` with the saved owner identity and remaining cleanup. The parent may already be stopped, or the plan marked cancelled, while descendants still await confirmation.

The task or cancelled-plan page displays the captured runs and offers **Retry remaining stops** and **Refresh progress**. If no targets remain but synchronization is still unconfirmed, **Confirm cleanup** checks the saved operation again. Recovery uses a new request against the saved operation UUID:

- `POST /api/tasks/stops/retry` with `{id, operation_id}`.
- `POST /api/plans/:id/retry-stops` with `{operation_id}`.

A changed operation returns `409` and requires a refresh. Original partial or uncertain receipt replies remain immutable; recovery observes current shared progress instead of replaying the original owner action. Plans cannot be archived and parents cannot be reopened while their cleanup remains unresolved. Confirmed cleanup releases those guards.

Each pending or unresolved row offers **Review this stop**. The preview shows its original captured identity and the current task records. **Include reviewed task** authorizes the displayed current attempt, including a replacement UUID that ordinary retry refuses to target. **Exclude from cleanup** leaves the task running and removes only this cleanup's matching stop marker. Both actions require a reason and explicit confirmation. The saved **Cleanup reviews** history distinguishes exclusion from a confirmed stop.

The primary advertises `family_reviews: 1` with its stop capabilities. It creates a preview through `POST /api/stops/review` with `{owner, operation_id, target_id}`. `POST /api/stops/resolve` adds `preview_digest`, `action`, `reason` and a stable `request_id`. A changed owner or operation, or changed identities in the reviewed task family, invalidates the preview with `409`. Resolution saves the authorization and audit; process shutdown still uses the exact-run coordinator. The UI retries remaining stops after a confirmed inclusion. Exclusions remain recorded with `stopped: false`, and background discovery honors them. Once all remaining cleanup is resolved and synchronized, audited exclusions can release archive/reopen guards while excluded tasks continue running.

**Check same review** reuses the original decision after a lost reply or partial save. Closing the dialog or navigating away keeps the pending decision; **Check pending cleanup review** reopens it on the owner page. Its request identity prevents duplicate audit entries or retargeting, even after the row was removed or the included attempt stopped. A new cloud request may get a new transport ticket to publish the existing decision; its original partial reply remains unchanged. **Refresh review** obtains a new preview for a new decision.

On daemon restart, interrupted runs are stopped and rechecked against fresh metadata. A matching stop intent settles that exact run as cancelled or done instead of requeueing it. Recovery is installed before the machine advertises task-control readiness. The primary also retries saved cleanup during its normal lifecycle, outside the scheduler's file lock.

Tests use local fixture commands, temporary data and the production Worker. They verify process-tree exit before success, stale-run rejection, late-result suppression, lost replies, partial saves, machine authority and desktop/phone recovery. `cloud/test/stop-batches.ts` adds real RemoteFiles synchronization between separate DATA mirrors, parent/child/grandchild stop capture, hard daemon restart, failed publication, explicit retry, immutable original replies, and archive/reopen guards. The fixture processes share a physical filesystem; their task data reaches other mirrors through the Worker, without manual copies. An unavailable channel is simulated by pausing its bridge and withdrawing task-control support; heartbeat expiry is covered by focused tests.

The same integration verifies stale review rejection, explicit replacement-run inclusion, replay after a lost first reply and after failed publication, one durable audit per decision, exclusion of both pending and unresolved rows, and archive while excluded processes remain alive. It checks that background discovery does not restore excluded rows or create terminal records claiming they stopped.

Real process execution was verified on macOS. Windows uses `taskkill /T /F` and fails closed on an unsuccessful exit, but has not been exercised on a Windows host.
